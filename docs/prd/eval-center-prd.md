## 一、产品背景与目标

### 1.1 背景

EvoFlow 作为 AI Agent 框架，当前缺乏一套**基于真实业务数据的端到端评测体系**：

- 发版前只能靠人工点测，不知道新版本会不会把核心功能搞崩
- 知识库质量、Agent 任务完成率、工具调用成功率等关键指标无法量化
- 安全权限（越权、注入、数据泄露）没有系统化的检测手段
- 性能问题（响应慢、并发卡）只能靠用户反馈，无法主动发现

### 1.2 目标

建设 **EvoFlow 评测中心（Eval Center）**，实现：

1. **业务可量化** — 用真实对话/任务数据计算任务完成率、工具成功率、知识库命中率等核心指标
2. **安全可审计** — 自动化检测越权、注入、数据泄露、沙箱逃逸等安全风险
3. **性能可回放** — 用真实流量回放压测，输出 P50/P95/P99 延迟分布
4. **版本可对比** — 每次发版自动对比上一版本，发现退化及时告警
5. **结果可视化** — 前端仪表盘直观展示健康度，支持下钻到具体问题

### 1.3 核心用户

| 用户角色 | 核心诉求 |
|---------|---------|
| **研发工程师** | 发版前跑回归，定位性能瓶颈，复现失败用例 |
| **运维/安全** | 安全审计、漏洞检测、权限合规检查 |
| **产品/运营** | 看业务质量趋势、Agent 表现排行、用户满意度 |
| **管理员** | 全局健康度总览、告警配置、评测计划管理 |

## 二、使用场景

### 场景一：发版前回归检测

> 小王要发 v0.4.1，点击「一键评测」→ 选择「冒烟 + 安全扫描」→ 5 分钟出报告 → 确认无严重退化 → 放心发布

### 场景二：安全月度审计

> 安全负责人每月跑一次「全量安全评测」→ 输出安全审计报告 → 导出 PDF → 归档备查

### 场景三：性能优化验证

> 优化了知识库检索算法 → 用「性能回放」跑 1000 条真实 query → 对比优化前后 P95 延迟 → 确认提升 30%

### 场景四：日常健康监控

> 管理员每天早上打开评测中心首页 → 看健康度分数 → 发现红色告警 → 点击下钻定位问题

### 5.2 核心流程

#### 流程一：一键评测

```
用户点击「一键评测」
    → 前端调用 POST /api/eval/run
    → 后端 EvalRunner 接收任务
    → 根据配置加载对应 Evaluator
    → DataSource 从 DB 采集真实数据
    → 并行/串行执行评测用例
    → 实时推送进度（SSE/WebSocket）
    → 全部完成后生成报告
    → 写入 eval_runs 表
    → 触发告警规则检查
    → 返回评测结果
```

#### 流程二：定时评测

```
Scheduler 每分钟检查
    → 匹配到到期的评测计划
    → 触发评测执行（同流程一）
    → 执行完成后检查通知配置
    → 发送通知（飞书/邮件/站内信）
```

#### 流程三：告警触发

```
评测完成
    → AlertEngine 加载所有规则
    → 逐条匹配指标阈值
    → 命中 → 创建告警记录
    → 按级别通知对应渠道
    → 更新告警状态
```

## 六、数据模型设计

### 6.1 eval_runs（评测运行记录）

```sql
CREATE TABLE eval_runs (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,           -- 评测名称
    type TEXT NOT NULL,           -- 类型: smoke/full/security/performance/custom
    status TEXT NOT NULL,         -- 状态: pending/running/completed/failed
    triggered_by TEXT,            -- 触发人/触发方式: manual/schedule/api
    schedule_id TEXT,             -- 关联的评测计划ID
    config JSON,                  -- 评测配置
    summary JSON,                 -- 汇总结果（各维度得分）
    detail JSON,                  -- 详细结果（各用例结果）
    started_at TIMESTAMP,
    completed_at TIMESTAMP,
    duration_ms INTEGER,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 6.2 eval_cases（评测用例定义）

```sql
CREATE TABLE eval_cases (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    category TEXT NOT NULL,       -- 分类: business/security/performance/stability
    level TEXT NOT NULL,          -- 级别: smoke/full/stress
    description TEXT,
    evaluator TEXT NOT NULL,      -- 评测器名
    params JSON,                  -- 参数配置
    timeout INTEGER DEFAULT 30,   -- 超时时间(秒)
    severity TEXT DEFAULT 'medium', -- 严重程度: low/medium/high/critical
    enabled BOOLEAN DEFAULT true,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP
);
```

### 6.3 eval_schedules（评测计划）

```sql
CREATE TABLE eval_schedules (

    last_run_at TIMESTAMP,
    next_run_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP

```

### 6.4 alert_rules（告警规则）

```sql
CREATE TABLE alert_rules (
```

| **任务调度** | APScheduler / 现有 scheduler | 复用 EvoFlow 调度引擎 |
| **实时推送** | SSE / WebSocket | 评测进度实时推送 |
| **报告生成** | Jinja2 + HTML → PDF | 支持 HTML/PDF/JSON 三种格式导出 |
| **存储** | SQLite（与 EvoFlow 共用） | 评测数据写入 evoflow.db 新表 |

## 十、风险与依赖

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 真实数据脱敏不彻底 | 🔴 高 | 评测时对敏感字段自动脱敏，仅用于统计不展示原文 |
| 压测影响生产环境 | 🔴 高 | 压测模式使用独立实例，或在低峰期执行，带速率限制 |
| 安全扫描误报率高 | 🟡 中 | 建立白名单机制，支持人工标记误报 |
| 数据量太大统计慢 | 🟡 中 | 预计算 + 缓存，按天聚合，避免实时全表扫描 |
| 前端开发资源不足 | 🟡 中 | 优先复用可观测性模块组件，分阶段上线 |
